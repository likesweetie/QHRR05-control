# HW_deploy 구현 계획

작성: 2026-10-31. 시작점: `main`의 `68d7df5`(순차 스토퍼 제로셋 병합).

이번 변경은 계획 문서까지입니다. 아래 실행 옵션·상태 전이·하드웨어 프로파일은 아직 구현하지 않았으며, 이번 작업에서 빌드·시험·실물 CAN 송신은 실행하지 않습니다.

## 목표와 원칙

실제 SocketCAN과 모터로 같은 TaskController를 구동합니다. MuJoCo는 **측정한 관절 상태로 기구학·동역학을 계산하는 라이브러리**로 유지하고, 물리 시뮬레이터·가상 모터·렌더러는 실행 및 빌드 의존성에서 분리합니다.

- 안전 정책은 현재 `src/safety` 한 곳에서 읽을 수 있게 유지합니다. 안전 전용 프로세스, 병렬 감시기, 계층별 정책 복제는 추가하지 않습니다.
- 입력 승인과 실제 모터 송신의 책임을 구별합니다. HAL의 패킷 검증·통신 기한 처리는 별도의 모션 정책 계층으로 확장하지 않습니다.
- 실행 모드는 설정에 명시합니다. 시뮬레이터 연결 유무, 인터페이스 이름, 오류 발생 여부로 모드를 추측하거나 전환하지 않습니다.
- 기존 디렉터리를 유지합니다. `hardware/`, `platforms/`, `backends/`, `safety_layers/` 같은 병렬 트리나 범용 플러그인 구조를 만들지 않습니다.
- 파일을 여럿 거치는 설정 상속·자동 병합 없이, 실행 로그에 선택된 설정과 실제 적용값을 표시합니다.

## 1. 실행 모드와 시작 경로를 먼저 분리

세션의 `runtime_mode`는 `simulation | hardware` 두 값으로 정합니다. `--without-can`은 simulation 내부의 명시적 디버그 옵션으로만 남깁니다. hardware와 함께 지정하면 실패합니다.

daemon 설정이 모드의 원본이며 자식과 UI/로거가 동일한 세션 모드를 확인합니다. 필요하면 기존 SHM 세션 헤더에 작은 모드 필드를 추가하고 ABI를 올립니다. 시뮬레이션 참값이나 명령을 SHM으로 옮기지는 않습니다. 서로 다른 모드로 붙은 프로세스는 즉시 원인을 표시하고 종료합니다.

기존 위치에 다음 파일만 필요에 따라 추가합니다.

- `config/daemon/hardware.yaml`: `can_hal → control` 및 선택적인 input/logger. simulation 프로세스 없음. 기본 터미널 배치 없이 실행.
- `config/can_hal/hardware.yaml`: 실제 인터페이스·비트레이트 기대값·모터 ID·검증된 모터 프로파일.
- `config/control/hardware.yaml`: 기존 control 스키마를 그대로 사용하는 명시적 실기 게인·한도·제로셋 설정. simulation 설정을 자동 상속하지 않음.
- `scripts/run_hardware.sh`: 기존 daemon 호출을 감싸는 짧은 런처. vcan 생성, 네트워크 네임스페이스 생성, 자동 bitrate 변경, 임의 sudo 설정을 하지 않음.

실제 인터페이스가 없거나 DOWN, 종류/비트레이트가 설정과 다르면 구체적인 오류를 표시합니다. 이미 준비된 인터페이스를 읽고 사용합니다. `--existing-can`을 하드웨어 배포 완료로 간주하지 않습니다.

시작 직후는 **출력 비활성**입니다. 현재처럼 C4가 확인됐다는 이유만으로 TaskController가 자동 enable 요청을 켜지 않도록 바꿉니다. 프로세스 재시작도 자동 arm으로 이어지지 않습니다.

## 2. 시뮬레이션 전용 처리를 작은 경계로 이동

TaskController의 공통 루프는 다음만 수행합니다.

```text
Input 요청 → 공통 안전 판정 → TaskController
                              ↓
CAN 측정값 → 좌표 변환 → MuJoCo 계산 백엔드 → 모션 계산 → 출력 승인 → HAL
```

simulation IPC 구독/명령 전송, pause/reset/step/perturb, 자동 제로셋 시작과 외부 물체 접촉 거부는 기존 폴더 안의 작은 시뮬레이션 보조 파일로 모읍니다. 예를 들어 `src/control/simulation_support.*` 한 쌍으로 시작하고, 필요 이상으로 인터페이스·상속 구조를 늘리지 않습니다. 공통 SafetyLayer와 InputCommand가 시뮬레이션 자료형을 직접 들고 다니지 않도록 전용 파싱/검증을 이 경계로 옮깁니다.

hardware에서는 이 보조 객체와 소켓을 생성하지 않습니다. 연결 실패를 무시하며 계속 Poll하는 방식이나 항상 성공하는 빈 대체 객체를 쓰지 않습니다. 시뮬레이션 명령을 보내면 `hardware runtime does not support ...`처럼 명시적으로 거부합니다.

기본 빌드는 기존 동작을 유지하고, `QHRR_BUILD_SIMULATION=OFF`로 하드웨어 대상만 구성할 수 있게 합니다. 이 구성에서는 simulation/virtual motor 타깃·테스트·GLFW/OpenGL/Filament를 요구하지 않습니다. 현재 daemon의 X11 배치 기능도 선택적으로 제외하고, 제외된 빌드에서 해당 기능을 요청하면 오류를 냅니다. 기존 타깃과 소스 목록을 조건화하며 별도 프로젝트를 복제하지 않습니다.

MuJoCo 라이브러리는 계산 백엔드이므로 남깁니다. hardware 제어 경로에서 `mj_step`, 시뮬레이션 qpos, 접촉 GT를 호출하거나 참조하지 않습니다. 실제 로봇의 질량·관성·축·기어비·제로 프레임은 명시적 설정으로 확인합니다.

## 3. 작고 고정된 안전 계약

운전 상태는 `DISARMED / ACTIVE / FAULT` 세 개로 제한하고 TaskController 한 곳이 소유합니다. 기존 SafetyLayer는 입력·상태·출력에 대한 판단을 반환합니다. 별도 안전 스레드나 중첩 상태 머신을 추가하지 않습니다.

| 사건 | 결과 | 판단 위치 |
| --- | --- | --- |
| 알 수 없는 명령, 잘못된 형식·범위 | 요청 거부, 이유 기록. 마지막 승인 입력의 의미를 바꾸지 않음 | SafetyLayer |
| 명시적 Arm | 필요한 준비 조건을 만족할 때만 ACTIVE. 모드 선택만으로 arm하지 않음 | SafetyLayer → TaskController |
| Release 또는 정상 종료 | DISARMED, 이전 목표 폐기, HAL에 release 요청 | TaskController |
| 비유한 측정/계산 출력, 운전 범위 위반 | FAULT, 출력 해제 요청. 자동 재시도 없음 | SafetyLayer → TaskController |
| 명령 발행 중단, 특정 축의 피드백 중단, 송수신 실패 | 마지막 목표를 계속 재전송하지 않고 전 축 release 시도, 통신 fault 표시 | CAN HAL |
| 명시적 Fault clear | 원인이 해소됐으면 DISARMED까지만 복귀. 별도의 Arm 필요 | TaskController 및 HAL의 통신 상태 확인 |

모션의 workspace/IK 검사와 제로셋의 이동량·시간·접촉 조건은 해당 모션에 남깁니다. 이를 SafetyLayer에서 다시 계산하지 않습니다. 최종 출력 한도는 한 설정을 원본으로 사용하고, HAL은 실제 코덱/모터 프로파일의 표현 가능 범위를 검증합니다.

명령·피드백 기한은 **HAL 한 곳**에서 CLOCK_MONOTONIC 기준으로 검사합니다. 각 축의 `received_ns`와 제어기의 `command_published_ns`를 사용하며, 반복 송신 자체로 명령의 유효 기간을 연장하지 않습니다. GUI·daemon·logger에 같은 운전 중단 감시기를 복제하지 않습니다. 기한 값은 실측 주기·지연을 바탕으로 하드웨어 설정에 명시하며, 현재 시뮬레이션 수치를 임의로 이식하지 않습니다.

SHM 읽기가 막힌 동안에도 HAL의 통신 기한을 검사할 수 있어야 합니다. 출력 읽기는 현재처럼 무기한 mutex 대기에 묶이지 않도록 제한합니다. fault 뒤 새 명령이 들어왔다는 이유만으로 자동 C1 재전송을 재개하지 않습니다. 통신 상태 원본은 HAL이 갖고 제어기/UI는 그 상태를 읽습니다.

Arm 전 피드백을 읽는 방법도 실물 프로토콜 확인 대상입니다. 현재 가상 모터는 release 상태의 무출력 C0에 응답하지만 이를 실물에도 가정하지 않습니다. 실제 펌웨어의 조회 명령 또는 명시적 Arm 트랜잭션 내 무출력 준비 절차를 확인한 뒤 한 방식만 구현합니다. 확인 없이 C1을 주기적으로 보내며 준비 상태를 추측하지 않습니다.

CAN 단절 상태에서는 C2가 실제 모터에 도달했다고 보장할 수 없습니다. 모터 내 통신 타임아웃과 물리 전원 차단/비상정지는 실물에서 확인할 항목이며, 이를 대신한다고 주장하는 추가 소프트웨어 계층은 만들지 않습니다.

## 4. 좌표·제로셋·실기 제어값

좌표 변환은 기존 control I/O 경계 한 곳에 둡니다. `motor_ids`의 관절 순서, 회전 부호, 펌웨어의 입력축/출력축 단위, 감속비, 토크 부호를 확인하고 양방향 변환이 정확히 대응하게 합니다. 모션별로 부호를 다시 적용하지 않습니다.

하드웨어 제로셋은 시뮬레이션의 `require_zero_position_setup`이나 접촉 GT를 읽지 않습니다. 기존 ZeroSetController의 엔코더·속도·측정 토크 기반 탐색을 재사용하되, 실제 스토퍼 방향·각도·노력 상한을 하드웨어 프로파일에 명시합니다. 미보정 상태의 Arm은 명시적으로 선택한 Zero set에만 허용하고, 일반 모션은 좌표 보정 완료를 요구합니다. 하드웨어에서 자동 스토퍼 탐색은 하지 않습니다.

첫 배포는 런타임 오프셋만 사용합니다. ROM 쓰기나 세션 간 보정값 복원은 별도 요구가 생기기 전까지 추가하지 않습니다. 보정됐다는 사실과 offset을 표시하며, 과거 세션의 원점을 현재 원점으로 추측하지 않습니다.

현재 시뮬레이션의 damping/friction 값은 실측값이 아닙니다. 실기 프로파일은 마찰 보상·ILC를 비활성화한 기준 상태부터 확인합니다. 토크 한도·Kt·전류 방향·물리 관성 확인 후 필요한 항목만 켭니다. 특히 현재 공통 60.7Nm를 하드웨어의 승인된 한도로 간주하지 않습니다.

## 5. UI·로깅·시각화

기존 웹 UI와 Input 경로를 그대로 씁니다. Arm/Release/Fault clear, 운전 상태, 제로셋 상태, 마지막 거부 이유, 통신 fault를 표시합니다. UI가 정한 안전 판정 결과를 신뢰하지 않고 실제 상태의 원본은 제어기/HAL로 둡니다.

하드웨어 세션에서는 pause/reset/step/perturb와 접촉 GT 표시를 사용할 수 없다고 명시합니다. 무응답을 성공으로 표시하거나 값을 0으로 채우지 않습니다. 시뮬레이션 단축키를 모터 reset 같은 다른 동작으로 재사용하지 않습니다. UI 연결 해제가 독립적인 정지 감시기로 변하지 않도록, 승인된 모션은 정의한 수명대로 실행하고 Release는 명시적 입력으로 유지합니다. 연속 조작 입력의 유효 시간은 필요한 모션에서만 정의합니다.

로거의 기존 hardware 모드를 재사용합니다. 시뮬레이션 GT 누락은 하드웨어에서 오류가 아니며, 실제 CAN q/dq/Iq·환산 토크·명령·운전/통신 상태를 기록합니다. 모드를 연결 상태로 자동 감지하지 않습니다.

Filament는 선택적인 관측 도구로 둡니다. 하드웨어 snapshot은 motor/model/control sequence로 갱신하고, 측정 관절각으로 렌더링 전용 데이터의 FK만 갱신합니다. simulation IPC·물리 적분·가짜 접촉 데이터는 필요하지 않습니다. viewer나 로거의 종료를 모터 정책에 묶지 않습니다. 하드웨어 프로파일에서는 제어기/HAL 자동 재시작과 자동 재-arm을 금지하고, 선택적 UI/로거만 독립적으로 재시작할 수 있게 합니다.

변경은 위 묶음별로 작게 커밋합니다. 구조 재배치보다 실행 경로와 책임을 먼저 정리하고, 실제 중복이 확인된 코드만 옮깁니다. 검증 항목은 후속 구현의 완료 기준으로 기록했으며 이번 커밋·병합 작업에서는 사용자의 요청대로 별도 시험을 실행하지 않았습니다.
