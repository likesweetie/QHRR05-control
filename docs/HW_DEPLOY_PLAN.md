# HW_deploy 구현 계획

갱신: 2026-10-31. 시작점: `main`의 `68d7df5`(순차 스토퍼 제로셋 병합).

사용자 수정 방향을 반영해 실행 경로·데이터 계약·SHM 및 입출력 경계를 구현했습니다. 모션 제어식과 기존 그래픽 빌드 타깃은 유지했습니다. 실제 물리 CAN/모터를 연결한 검증은 후속 실기 단계이며, 이번 소프트웨어 완료 기준은 하드웨어 파이프라인에 vcan0 장치만 대체한 검증입니다.

대시보드 후속 변경으로 현재 SHM ABI는 16입니다. 개별 모터 Enable은 중립 출력 ARMED 상태를 사용하며, 기존 Arm은 전체 모션을 시작합니다. 기본 daemon은 웹 GUI도 실행하고, 웹은 제어 스택을 중지해도 유지되어 다시 시작할 수 있습니다. 상세한 명령/프로세스 정책은 [웹 문서](web_gui.md)에 있습니다.

## 구현 상태와 최종 검증

- 기본 `run_daemon.sh`/daemon/CAN 설정은 물리 can0를 사용하며 simulator/vcan을 시작하지 않습니다. `run_simulation.sh`가 별도로 vcan과 기존 MuJoCo OpenGL GUI를 시작합니다.
- `run_simulation.sh`가 vcan과 시뮬레이터를 실행하고, `run_visualization.sh`는 기본적으로 현재 장치 세션을 관측합니다. 새 시뮬레이션 시각화는 `--simulation`으로 선택합니다.
- SHM ABI 15에 supported/valid, coordinate_valid, measurement_ns, 모델 입력 sequence/가속도 유효성, drive state와 transport fault를 추가했습니다.
- TaskController의 simulation IPC/GT 참조를 입력 인터페이스로 옮겼습니다. 모션 클래스의 수치 계산 코드는 변경하지 않았습니다.
- Arm/Release/Clear fault와 HAL 한 곳의 명령·피드백 기한, 무기한 SHM 잠금 회피를 구현했습니다. 시작은 DISARMED입니다.
- `scripts/run_hw_deploy_test.sh`가 하드웨어 설정을 그대로 사용하고 CAN 인터페이스만 vcan0로 바꾼 뒤 기존 `simulation` 프로세스를 추가합니다. 기본값은 기존 MuJoCo OpenGL 창이며 `--verify`는 같은 실행 파일의 `--headless`를 사용합니다. 별도 물리/GUI fixture는 제거했습니다. 하드웨어 세션에는 시뮬레이션 IPC/GT/자동 보정 데이터를 제공하지 않습니다.
- 검증은 시뮬레이션 기능 부재, 미보정 상태, 명시적 Arm, 순차 제로셋, 호밍, Release, 제어기 중단에 대한 HAL 만료, 명시적 fault 해제 후 비활성 상태를 확인합니다.
- 2026-10-31 검증 결과: 최종 HW_deploy 시험 58.33초 통과. CAN HAL 통신·프로세스 수명·버스 점유율을 포함한 관련 CTest 19종, 웹 통합 2종, 시각화 스냅샷 시험을 통과했습니다. 실제 물리 CAN/모터 시험과 전체 회귀 시험 완료를 뜻하지 않습니다.

```bash
./scripts/run_hw_deploy_test.sh                          # 호스트 vcan0 + OpenGL 직접 조작
./scripts/run_hw_deploy_test.sh --verify                 # 호스트 vcan0 자동 검증
./scripts/run_hw_deploy_test.sh --verify --isolated-vcan # 독립 vcan 자동 검증
```

이하 항목은 구현의 설계 근거와 후속 실기 검증 기준입니다.

## 목표와 원칙

프로그램의 기본 운용은 **물리 CAN과 실제 모터**로 정합니다. vcan과 MuJoCo 물리 시뮬레이터는 시뮬레이션용 bash 파일을 실행했을 때만 사용합니다. 같은 PC에서 실기 운용과 시뮬레이션 시험을 모두 할 수 있도록 GLFW·시뮬레이터·시각화 빌드 타깃은 유지합니다.

이번 전환의 중심은 제어식 변경이 아니라 **입출력 인터페이스의 데이터 의미와 취득 가능 여부**입니다. 모션 제어기는 입력이 실제 로봇에서 왔는지 가상 모터에서 왔는지 몰라야 합니다. 동일한 유효 데이터와 설정을 받으면 같은 제어 결과를 냅니다.

- 기존 모션의 제어식, 수치 연산, 궤적 생성, IK/RFOB를 재작성하지 않습니다.
- 출처 구분은 데이터 생산자·인터페이스·UI·로깅에 둡니다. 모션 API에 `is_simulation`을 전달하지 않습니다.
- 취득 불가, 아직 미수신, 오래된 값, 정상적인 0을 구분합니다. 없는 센서를 0이나 시뮬레이션 참값으로 대신하지 않습니다.
- 안전 정책은 얇고 예측 가능하게 유지합니다. 여러 안전 프로세스나 중첩된 정책 계층을 추가하지 않습니다.
- 기존 디렉터리를 유지합니다. 필요하면 현재 폴더 안에 파일을 추가하며 병렬 hardware/simulation 소스 트리를 만들지 않습니다.
- 하드웨어용 CMake 타깃 조건화나 GLFW 제거를 하지 않습니다. 실행할 프로세스를 스크립트에서 선택합니다.

## 1. 물리 CAN 기본 실행, 시뮬레이션은 스크립트로 선택

별도 `run_hardware.sh`를 기본 런처에 덧붙이는 대신 기존 기본 실행 경로를 물리 CAN 기준으로 바꿉니다.

| 실행 파일 | 계획된 역할 |
| --- | --- |
| `scripts/run_daemon.sh` | 물리 CAN으로 can_hal/control 및 필요한 input/logger 실행. 시뮬레이터나 vcan을 만들지 않음 |
| `scripts/run_simulation.sh` | vcan 준비 및 같은 can_hal/control에 MuJoCo 시뮬레이터·가상 모터를 연결 |
| 기존 시각화 스크립트 | 선택한 세션을 관측. 물리 시뮬레이터 동반 실행은 시뮬레이션 실행 경로에서 명시 |

`config/daemon/daemon.yaml`과 `config/can_hal/can_hal.yaml`은 물리 CAN 기본 설정입니다. 시뮬레이션 실행 목록과 vcan 설정은 `scripts/simulation_config.py`가 이 두 파일에서 임시 생성하며 복제 YAML을 두지 않습니다. 기존 가상 모터·센서 설정 `config/simulation/simulation.yaml`은 유지합니다. HW 테스트와 일반 시뮬레이션도 같은 `simulation` 실행 파일을 사용합니다.

물리 CAN 이름·비트레이트·ID는 설정으로 지정합니다. 기본 스크립트는 준비된 인터페이스를 확인하며, 장치가 없거나 설정과 다르면 이유를 표시하고 실패합니다. vcan 생성이나 시뮬레이터 실행으로 대체하지 않습니다. 현재 `--existing-can`은 시뮬레이터 프로세스까지 제거하지 않으므로 새 기본 운용을 대신할 수 없습니다.

`--without-can` 직접 토크 경로는 명시적 시뮬레이션 디버그 기능으로만 남깁니다. 이 경로가 제공하지 않는 전류·CAN 상태는 취득 불가로 표시합니다. 실제 모터와 vcan은 정상 운용에서 같은 SocketCAN 명령/피드백 계약을 사용합니다.

공통 제어 설정은 우선 `config/control/control.yaml` 하나를 유지합니다. 실험별 설정이 필요하면 사용할 파일을 명시적으로 선택하며 자동 상속·겹쳐 쓰기 체계는 만들지 않습니다. 단순히 물리/시뮬레이션이라는 이유로 제어 설정 전체를 복제하지 않습니다.

## 2. 데이터를 실제 관측·계산·시뮬레이션 참값으로 구분

물리적으로 얻을 수 있는 신호와 그 신호에서 계산한 값은 다릅니다. 아래 의미를 인터페이스·UI·로그에서 유지합니다.

| 데이터 | 실제 로봇에서의 의미/취득 조건 | 시뮬레이션에서의 대응 | 모션 제어 입력 |
| --- | --- | --- | --- |
| 원시 엔코더 위치·속도 | 펌웨어가 반환한 CAN 피드백 | 가상 모터의 같은 CAN 피드백 | 같은 단위·축 순서로 제공 |
| Iq·온도 | 해당 펌웨어/장치가 제공할 때만 유효 | 가상 센서/모터 피드백 | 필요한 채널의 유효성으로 판단 |
| 관절 좌표 | 엔코더값과 유효한 영점/축 변환으로 계산 | 동일한 변환으로 계산 | 출처와 무관한 공통 q/dq |
| 모터 토크 | 현재 구현은 Iq×Kt 환산값. 직접 토크 센서값이 아님 | 가상 Iq×같은 환산 규약 | 환산 근거와 입력이 유효할 때 제공 |
| 관절 가속도 | 현재 구현은 속도 차분 추정 | 같은 차분 경로 | 샘플 간격·이력 조건 충족 시 유효 |
| M/bias/J·중력·발끝 FK | 측정 q/dq와 설정된 모델로 계산 | 같은 모델 백엔드로 계산 | 공통 모델 계산값 |
| RFOB 외력·접촉 추정 | 관측값과 모델에서 추정 | 같은 관측기로 추정 | 추정 유효성 유지. 참값과 구분 |
| 실제 q/속도/actuator torque GT | 현 구성에서 직접 취득 불가 | MuJoCo 물리 참값 | 공통 제어 입력에 포함하지 않음 |
| 접촉력 GT·물체 pose·외란 wrench | 대응 센서가 없는 현재 구성에서는 취득 불가 | 시뮬레이터가 직접 제공 | 시뮬레이션 관측/검증용 별도 데이터 |
| 조이스틱·작업 명령·가상 목표점 | 사용자가 지정한 명령. 센서 측정값이 아님 | 같은 입력 계약 | 기존 Input 경로 유지 |

향후 센서가 추가되면 그 채널의 취득 가능 여부와 실제 측정값을 등록합니다. 예를 들어 외력 센서가 생겼다고 기존 RFOB 추정이나 `contact_force_gt`를 조용히 교체하지 않습니다. 측정·추정·참값의 의미를 별도로 유지합니다.

MuJoCo 계산 라이브러리는 양쪽에서 그대로 사용합니다. 계산된 발끝 위치는 측정된 발끝 위치라고 표시하지 않고, 시뮬레이션의 `qpos`를 CAN 관절값 대신 제어기에 넣지 않습니다.

## 3. 인터페이스의 취득 가능 여부를 기준으로 SHM 정리

SHM을 두 벌의 물리용/시뮬레이션용 구조로 나누지 않습니다. 현재 `MotorData / ModelData / ControlData`를 중심으로 필요한 상태만 보강합니다. 시뮬레이션 전용 데이터 교환은 기존 `src/ipc/simulation` 파이프라인을 유지합니다.

먼저 데이터 묶음마다 아래 계약을 명확히 합니다.

| 구분 | 의미 | 예시 |
| --- | --- | --- |
| 취득 가능 `supported` | 생산자가 해당 신호를 제공할 수 있는가 | 직접 토크 디버그에서는 Iq 취득 불가 |
| 현재 유효 `valid` | 이번 관측을 사용할 수 있는가 | 지원되는 엔코더라도 첫 응답 전에는 무효 |
| 샘플 식별·시각 | 어느 관측이며 얼마나 오래됐는가 | CAN 축별 sequence/monotonic timestamp |
| 좌표 보정 유효성 | 원시 엔코더를 관절 좌표로 해석할 수 있는가 | 수신은 정상이어도 미제로셋 q는 아직 관절 좌표로 무효 |
| 출처 설명 | 장치 응답·가상 장치 응답·계산·참값 구분 | UI/로거/진단용이며 모션의 분기 조건이 아님 |

최소 변경안은 기존 축별 `received_sequence / received_ns`를 재사용하고 필요한 채널별 supported/valid 마스크, 영점 유효성, 모델 계산이 소비한 측정 sequence를 보강하는 것입니다. 모든 스칼라를 별도 클래스나 여러 enum 상태 머신으로 감싸지 않습니다. 같은 CAN 프레임의 위치·속도처럼 함께 갱신되는 항목은 묶어서 관리합니다.

- `can_enabled`나 시뮬레이터 연결 여부를 전류·위치 데이터의 유효성으로 사용하지 않습니다.
- `MotorData`에는 장치 관측과 그 규약에 따른 환산값, `ModelData`에는 명시적인 모델 계산값을 둡니다. 계산 결과에는 입력 관측의 식별자를 연결해 최신 관측과 오래된 계산값이 섞이지 않게 합니다.
- 원시 엔코더가 유효한 상태와 보정된 관절각이 유효한 상태를 구분합니다. 제로셋은 전자의 위치/속도/환산 토크를 사용할 수 있고, 일반 모델 기반 모션은 후자를 요구합니다.
- 제공 불가와 미수신/오래됨은 다른 상태입니다. 오래된 값은 표시용으로 보관할 수 있어도 현재 제어 입력으로 유효하다고 표시하지 않습니다.
- UI는 값과 상태를 함께 표시합니다. 숫자 0, 취득 불가, 미수신, 오래된 샘플을 같은 모양으로 내보내지 않습니다.
- 물리 CAN/vcan이라는 출처 설명은 진단 메타데이터에 한정합니다. 모션 제어기에 전달하는 공통 관측에는 필요한 값·유효성·샘플 정보만 남깁니다.
- 실제 SHM 레이아웃/의미가 바뀔 때 ABI를 올리고 모든 참여 프로세스가 불일치를 명시적으로 거부하게 합니다.

이 정리는 SHM·입출력 어댑터 경계에 집중합니다. 모션별로 SHM을 직접 읽거나 별도 센서 선택 로직을 추가하지 않습니다. 영점 보정, 단위, 축 부호, 모델 갱신의 기존 경계도 중복 구현하지 않습니다.

## 4. 제어 처리는 유지하고 입출력에서 차이를 흡수

공통 경로는 다음과 같습니다.

```text
실제 모터 또는 가상 모터 → CAN HAL → 공통 관측 SHM → 입력 인터페이스
                                                          ↓
                                    유효 관측 → MuJoCo 모델 계산 → 기존 모션 제어
                                                          ↓
                                             공통 출력 → CAN HAL

MuJoCo 물리 참값 → simulation IPC → 관측/로깅/시뮬레이션 조작 인터페이스
```

TaskController에서는 `ReadInput`/`WriteOutput` 주변의 데이터 취득·검증·변환 계약을 정리합니다. 기존 Compute/궤적/IK/동역학 제어 경로를 물리용·시뮬레이션용으로 복제하지 않습니다. 각 모션은 필요한 입력 종류를 요구할 수 있지만 데이터의 물리/가상 출처를 검사하지 않습니다.

현재 TaskController 안의 simulation IPC Poll, pause/reset/perturb 전달, `require_zero_position_setup` 기반 자동 시작, GT 외부 접촉 검사는 기존 `src/interfaces`·`src/ipc/simulation` 경계로 옮기는 대상으로 봅니다. 이를 위해 별도 `src/control/simulation_support` 계층이나 새로운 통합 프레임워크를 만들지 않습니다.

- 자동 제로셋이 필요한 시뮬레이션 시작은 시뮬레이션 인터페이스가 일반 Zero set 요청으로 전달합니다. 모션에는 `require_zero_position_setup`을 전달하지 않습니다.
- 제로셋의 엔코더·속도·토크 기반 탐색과 후퇴 제어는 재사용합니다. 하드웨어에서는 실제 영점 유효성/운영자 요청에 따라 같은 절차를 실행합니다.
- 기존 GT 접촉 거부는 시뮬레이션 전용 사전 검사임을 UI에 명시하고 해당 인터페이스에서 처리합니다. 물리 로봇의 보편적인 접촉 센서처럼 공통 제어 경로에 넣지 않습니다.
- pause로 관측 시계가 멈추는 경우에도 시간 간격·새 샘플 여부·실행 허용 상태를 공통 인터페이스 계약으로 전달합니다. 모션 함수에 시뮬레이션 전용 시간 분기를 추가하지 않습니다.
- 모션에 필수인 입력이 없으면 시작 요청을 거부하고, 실행 중 유효성이 사라지면 정해진 공통 정지 계약을 적용합니다. 모델 예측이나 GT로 채워 계속 동작시키지 않습니다.

작은 관측 묶음/기존 구조체를 재사용하고, 출처마다 별도의 MotionController 상속 구조나 범용 센서 라우터를 만들지 않습니다.

## 5. 얇고 예측 가능한 안전 계약

이전 계획의 단순한 Arm/Release와 통신 기한 책임 분리는 유지하되, 배포 전환을 이유로 제어 알고리즘이나 모션별 정책을 다시 설계하지 않습니다.

- 공통 SafetyLayer는 명령 형식·유한값·설정 범위·필수 데이터 유효성을 판단합니다. 같은 유효성 결과에 출처별로 다른 판정을 내리지 않습니다.
- 필요한 운전 상태만 `DISARMED / ACTIVE / FAULT`로 명확히 관리합니다. 단순 모드 선택이나 프로세스 재시작으로 자동 arm하지 않습니다.
- 모션의 workspace/IK 검사와 제로셋의 이동량·시간·접촉 기준은 기존 모션의 책임으로 유지합니다.
- 명령·CAN 피드백 기한은 HAL 한 곳에서 판정합니다. UI/daemon/로거에 중복 정지 감시기를 추가하지 않습니다. 출처는 진단에만 사용하고 정상적인 vcan 피드백에도 같은 계약을 적용합니다.
- 필수 피드백/계산값이 무효일 때 조용한 대체값을 내보내지 않습니다. 거부/정지 이유와 복귀 조건을 표시합니다.
- 새 명령이 왔다는 이유만으로 fault를 지우거나 재-enable하지 않습니다. C4/C1/C0/C2의 실제 지원 범위와 무출력 조회 가능 여부는 장착 펌웨어에서 확인합니다.

실제 장치의 데이터 제공 범위·단위·축 부호·Kt와 허용 한도를 먼저 확인합니다. 시뮬레이션 센서나 모델에서 쓸 수 있던 항목을 실측값으로 간주하지 않으며, 현재 제어 설정을 실기 검증 완료값이라고 선언하지 않습니다. CAN이 끊겼을 때 release 전달을 보장할 수 없다는 한계도 표시하며, 추가 소프트웨어 안전 계층으로 이를 가리지 않습니다.

## 6. UI·로깅·시각화와 빌드

웹 UI와 로거는 인터페이스가 제공한 데이터 설명과 유효성을 표시합니다. 공통 센서/계산값은 동일한 항목으로, 시뮬레이션 GT는 별도 항목으로 표시합니다. 센서가 없는 상태를 정상적인 0이나 미접촉으로 표현하지 않습니다.

시각화는 공통 q와 모델 FK만으로 실제 로봇도 표시할 수 있게 합니다. 시뮬레이션에서는 여기에 물리 GT·물체·외란 정보를 추가로 표시합니다. 관측 갱신 기준을 simulation sequence 하나에 묶지 않고 각 데이터의 생산 sequence를 사용합니다. pause/reset/perturb는 제공되는 세션에서만 활성화하며, 실제 모터의 reset/release로 키 의미를 바꾸지 않습니다.

GLFW, OpenGL, Filament, MuJoCo 물리 시뮬레이션 빌드 타깃은 유지합니다. **`QHRR_BUILD_SIMULATION=OFF`, 하드웨어 전용 빌드 그래프, X11 제거/조건화는 이번 계획에서 삭제합니다.** 같은 실기 컴퓨터에서 시뮬레이션 테스트를 할 수 있어야 합니다. 빌드 가능 여부와 평상시에 실행할 프로세스를 구분합니다.

로거의 기존 hardware 설정은 실제로 제공되는 데이터와 맞도록 정리합니다. mode 이름만으로 모든 채널이 있거나 없다고 결정하지 않습니다. 출처는 기록하되 관측/추정/GT의 유효성을 각각 보존하고, 시뮬레이션 전용 채널은 기존 별도 IPC에서 받습니다.

## 구현 순서와 완료 기준

| 순서 | 변경 묶음 | 완료 기준 |
| --- | --- | --- |
| 1 | 데이터 목록·소비 지점 정리 | 실제 관측/환산/추정/GT/명령, 취득 불가·유효성·시간 기준이 문서와 인터페이스에서 일치 |
| 2 | 기본 물리 CAN 실행과 시뮬레이션 bash 분리 | 기본 실행은 가상 장치나 시뮬레이터를 만들지 않음. 시뮬레이션 스크립트만 vcan과 물리 시뮬레이터를 실행 |
| 3 | 필요한 SHM 상태와 입출력 계약 보강 | 새 샘플·영점·모델 계산 유효성이 분명하고, 없는 데이터를 0/GT로 보충하지 않음 |
| 4 | 인터페이스로 시뮬레이션 처리 이동 | 모션 API/제어식은 공통으로 유지. 모션 코드가 물리/가상 출처를 검사하지 않음 |
| 5 | UI/로깅/시각화 연결 | 취득 불가·미수신·오래된 값·정상값 표시가 구분되고 시뮬레이션 없이도 실제 상태 관측 가능 |
| 6 | 최소 안전 계약과 실물 통신 확인 | 데이터 유효성 거부·명시적 enable/release·HAL 통신 기한이 한 책임 위치에서 동작 |
| 7 | 실기 제어 검증 | 단위/축/영점 확인 후 Damping → Homing → Gravity 순서로 확인. 같은 모션 코드로 시뮬레이션 회귀 확인 |

후속 구현에서는 동일한 공통 관측을 모션에 넣었을 때 출처에 무관하게 같은 결과가 나오는지, 미수신/취득 불가/오래된 데이터를 제대로 구별하는지, 기본 스크립트가 물리 시뮬레이터를 띄우지 않는지를 검증합니다. GLFW/시뮬레이션 빌드를 제거하는 검증 항목은 두지 않습니다.

변경은 기존 디렉터리 안에서 작게 나눕니다. 이번 구현에서는 빌드와 격리된 가상 CAN 검증을 수행하며 실제 물리 CAN 송신은 하지 않습니다. 실물 펌웨어·단위·한도 검증은 장치 연결 후 수행할 항목입니다.
